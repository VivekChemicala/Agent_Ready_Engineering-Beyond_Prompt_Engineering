# Agent-Ready Engineering: Beyond Prompt Engineering

A small, personal experiment on one question: **does making a repository
"agent-ready" (written rules, repository instructions, verification gates,
domain skills) improve what an AI coding agent delivers, compared with a plain
task prompt?**

> **Disclaimer.** This is an independent personal project. It contains no
> employer source code, internal architecture, proprietary data or
> confidential documentation. All business rules, "team conventions" and
> datasets were written from scratch for this experiment. It is not affiliated
> with or endorsed by any employer or vendor.

## Synthetic data only

Every dataset in this repository is **synthetic** and was generated for the
experiment:

| Project | Data | How it was made |
|---|---|---|
| `producer-validation/` | `data/synthetic_producers.json` | Hand-written fictional insurance producers. Every last name is `Synthetic`, emails use the reserved `example.com` domain, and NPNs and license numbers are random digits that do not refer to real people. |
| `txn-pipeline/` | `data/input/partition-*.jsonl` | Generated by `experiment/generate_sample_data.py` from a fixed random seed. IDs such as `cust-0020` and `merch-012` are placeholders. |

## Experiments

| | 1. `producer-validation/` | 2. `txn-pipeline/` |
|---|---|---|
| Task | Implement licensing rules BR-005..BR-009 | Build a Kafka-style ingestion and validation pipeline |
| Arms | basic prompt vs. harness (`AGENTS.md` + business-rules doc + pytest/flake8/rule-check fix loop) | basic prompt vs. prompt + `SKILL.md` (domain conventions) |
| Agent | Custom harness (`harness/`) calling the model API directly | Devin sessions (Devin.ai, `normal` mode) |
| Model | `claude-sonnet-4-6`, requested by the harness through the Anthropic Messages API, temperature 0 | **Not exposed by the platform.** Results describe Devin's behaviour in that mode, not any specific model. |
| Trials | 3 per arm | 3 per arm |
| Scoring | Held-out acceptance suite (decisions, contract, robustness) | Hidden acceptance suite (29 checks) + pytest/flake8/CLI gates, up to 2 scripted review rounds |
| Details | [`producer-validation/RESULTS.md`](producer-validation/RESULTS.md) | [`txn-pipeline/experiment/RESULTS.md`](txn-pipeline/experiment/RESULTS.md) |

### Model attribution

Only experiment 1 can be attributed to a named model, because the harness
chose the model ID in its own API calls. Experiment 2 ran inside Devin, which
did not report the underlying model, so its results should not be attributed
to Claude or any other specific model.

### Experiment 3: `polyrepo-context/`

Can an agent plan a cross-repo Jira story in a polyrepo? A synthetic 13-repo
data platform and one ticket that touches 10 repos. Four arms, 3 Devin
(`normal` mode) trials each: one repo only; + service catalog; + contracts and
architecture docs; all code side by side with no docs. Scored by a hidden
answer key and a blind plan reviewer. See
[`polyrepo-context/experiment/RESULTS.md`](polyrepo-context/experiment/RESULTS.md)
and the industry-practice notes in
[`polyrepo-context/INDUSTRY_PRACTICE.md`](polyrepo-context/INDUSTRY_PRACTICE.md).

| Arm | Repos found (of 10) | Planned work for a decommissioned repo | Plan score (of 16) |
|---|---|---|---|
| One repo + README | 6.7 | 3/3 | 9.0 |
| + catalog and dependency graph | 10.0 | 0/3 | 13.7 |
| + contracts and architecture docs | 10.0 | 0/3 | 16.0 |
| All code side by side, no docs | 9.7 | 3/3 | 15.0 |

## Results

| Metric | Exp. 1 basic | Exp. 1 harness | Exp. 2 basic | Exp. 2 skill |
|---|---|---|---|---|
| Correct accept/reject decisions | 3/3 trials | 3/3 trials | 6/6 requirements, every trial | 6/6 requirements, every trial |
| Contract compliance (first delivery) | 4–7/10 | 10/10 | 3–4/19 | 19/19 |
| Accepted on first delivery to the reviewer | 0/3 | 3/3 (after its internal fix loop) | 0/3 | 3/3 |
| Rework rounds | not applicable (one shot) | 1 extra fix-loop iteration in 1 trial | 5 total | 0 |
| Median cycle time | not measured | not measured | 5m42s | 3m39s |

What the two experiments share: the agents got the functional logic right in
both arms, and their own tests always passed. The basic arms failed on the
**contract** (exact codes, field names, edge-case rules), which their own
tests did not check. Writing that contract into the repository fixed it.

## Limitations

- Small samples (3 trials per arm). The direction is clear; the effect size is
  not measured precisely.
- Synthetic, small workloads written by the experimenter.
- The hidden suites test the same contract that the rules doc / skill states,
  so the result shows that stating conventions removes contract misses. It does
  not show the agents became better engineers in general.
- Temperature 0 was not fully deterministic in experiment 1.
- Experiment 2 has no cost data (the API reported 0 ACUs) and no model
  identity.

## Next experiments

- Structured specifications instead of prose task prompts.
- Repository-level instructions (`AGENTS.md`) vs. skills vs. both combined.
- Larger samples and human (not scripted) reviewers.
